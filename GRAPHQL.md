# GraphQL: catching up with a regenerated schema

`graphql/schema.graphql` is the backend's exported schema. It is the contract the frontend is type-checked against, and it is never edited by hand. When the backend API changes, re-export it and follow the steps below.

## How the pieces fit

```text
chatney-backend
    ↓ schema export
graphql/schema.graphql            committed, generated by the backend
    ↓ npm run graphql:generate    (config: codegen.ts)
src/graphql/generated/            committed, never edited by hand
    ↓ imported by
src/graphql/*.ts                  operations and fragments, written with graphql()
src/types/*.ts                    entity types, aliased to generated fragment types
```

## Steps

### 1. Re-export the schema

From the backend checkout:

```bash
dotnet run --project ChatneyBackend -- schema export --output ../chatney-frontend/graphql/schema.graphql
```

The export also writes `schema-settings.json` next to it. Nothing in the frontend uses that file; it is gitignored.

### 2. See what changed

```bash
git diff graphql/schema.graphql
```

Look for removed or renamed fields, new required fields on `input` types, nullability changes (`String` ↔ `String!`), and new `scalar` definitions.

### 3. Regenerate

```bash
npm run graphql:generate
```

This validates every operation in `src/` against the new schema before generating anything. If it fails, no files are written; fix the operations it names in `src/graphql/` and run it again.

### 4. Type-check and fix callers

```bash
npm run build
```

Operations that are still valid can produce different types, so the remaining breakage shows up here, in components, in `src/test-utils/fixtures/`, and in story mocks.

### 5. Lint and test

```bash
npm run lint
npm test
```

### 6. Commit together

Commit `graphql/schema.graphql`, `src/graphql/generated/` and the code fixes in the same commit. CI runs `npm run graphql:check`, which regenerates and fails if the committed generated files differ.

## Reading the errors

| Symptom | Where | Cause | Fix |
| --- | --- | --- | --- |
| `Cannot query field "x" on type "Y"` | step 3 | Field removed or renamed | Update the selection in `src/graphql/`, usually in a fragment |
| `Unknown type "XInput"` / `Unknown argument "x"` | step 3 | Input type or argument renamed | Update the operation's variable definitions |
| `Unknown scalar type` / scalar typed as `unknown` | step 3 | New custom scalar | Add it to `scalars` in `codegen.ts` (`strictScalars` is on) |
| `Not all operations have an unique name` | step 3 | Two operations share a name | Rename one; import the production document in stories instead of redeclaring it |
| `Property 'x' is missing in type … but required in type 'XInput'` | step 4 | New required input field | Pass it from the caller; if the value comes from the entity, add the field to its fragment |
| `Property 'x' does not exist on type 'XFieldsFragment'` | step 4 | Code reads a field that is not selected, or no longer exists | Add it to the fragment if the schema has it, otherwise remove the usage |
| `Type 'null' is not assignable to …` | step 4 | Field became nullable | Handle `null` at the point of use |
| Fixture or story mock errors | step 4 | Entity shape changed | Update `src/test-utils/fixtures/` and the `MockedProvider` mock data |

Do not paper over a mismatch by loosening `codegen.ts` or casting. If the frontend cannot satisfy the contract (for example a required input the schema gives no way to read), that is a backend gap to raise, not something to work around.

## Conventions

- Write operations with `graphql()` from `@/graphql/generated`, not `gql`. Every operation and fragment needs a unique name.
- Shared selections are fragments named `<Entity>Fields` (`UserFields`, `ChannelFields`, `MessageFields`). Spread them by name; no `${...}` interpolation is needed.
- When an `update…` mutation takes the whole entity as input, the entity's fragment must select every field that input requires.
- Do not hand-write response or variable types. Entity types in `src/types/` alias the generated fragment types, so a schema change flows through automatically.
- `DateTime` is a `string` on the client. Convert at the point of display.
- New fields used by the UI go into the fragment first, then `npm run graphql:generate` (or `npm run graphql:watch` while developing).
