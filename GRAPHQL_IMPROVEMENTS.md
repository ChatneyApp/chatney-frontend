# GraphQL Improvements

The first round of work is done: the frontend now has a committed backend schema, generated operation types, schema-aware linting, and CI that fails on contract drift. Apollo is still mostly used as a transport layer, though. The biggest remaining improvements are letting the Apollo cache own server state and paginating chat messages.

For the day-to-day workflow (refreshing the schema, regenerating, reading the errors), see [`GRAPHQL.md`](GRAPHQL.md). This document tracks what was recommended, what has been done, and what is left.

## Executive assessment

Current strengths:

- Apollo Client 4 and strict TypeScript provide a solid base.
- Authentication and upload links are centralized in [`src/contexts/GraphqlProvider.tsx`](src/contexts/GraphqlProvider.tsx).
- Operations are grouped by domain under `src/graphql`, all named, all written with the generated `graphql()` function.
- The backend schema is committed and is the single source of operation, variable, and entity types.
- GraphQL ESLint validates every operation against the schema, and CI fails if generated files are stale.

The GraphQL layer is still not ready for long-term ownership by a large team because it lacks:

1. A deliberate Apollo cache strategy.
2. Pagination for potentially large datasets.
3. Consistent errors, testing, observability, and schema-release governance.

## Should the frontend import the backend schema?

Yes, and this is now how it works: the backend's generated executable schema is committed as a build artifact, not referenced through a relative path to somebody's backend checkout.

```text
Backend source
    ↓ make gen-schema (chatney-backend)
graphql/schema.graphql
    ↓ GraphQL Code Generator
typed frontend operations
    ↓ frontend CI
schema validation + TypeScript build
```

Rules for the committed `graphql/schema.graphql`:

- [x] It is generated by the backend and never hand-edited.
- [x] Frontend CI validates every operation against it.
- [ ] It represents a known backend revision or release. Nothing records which backend commit a given schema came from.
- [ ] A backend command or CI job refreshes it deterministically. The command exists (`make gen-schema`), but it is run by hand and writes into a sibling `../chatney-frontend` checkout.
- [ ] Backend CI checks whether a schema change breaks registered frontend operations. Backend CI currently runs unit tests only.

Later, when the projects and teams grow, publish the schema through one of:

- A versioned `@chatney/api-schema` package.
- A schema registry such as GraphOS or GraphQL Hive.
- A cross-repository CI artifact pinned to a backend commit.

Avoid using a live development endpoint as the only Codegen schema source. That makes builds dependent on whichever backend happens to be running and prevents reproducible CI.

## Findings

### 1. Manual types can lie about the API — ✅ Done

Response and variable types are no longer handwritten. Documents are typed by Codegen, and the entity types in `src/types` are aliases of generated fragment types (for example `Message` in [`src/types/messages.ts`](src/types/messages.ts)), so a schema change flows through automatically.

The discrepancies the original review flagged are gone:

- GraphQL timestamps are `string` (`DateTime` scalar), converted at the point of display.
- `ChannelGroup.workspaceId` is a `number`, matching `Int!`.
- The broken `GET_CHANNEL` query (`GetChannel`, `Id`, `Name`) was removed.
- Mutation variables are typed through `TypedDocumentNode`.

Left over: `CreateMessageDto`, `UpdateMessageDto`, and `CreateMessageInput` in [`src/types/messages.ts`](src/types/messages.ts) are still shaped by hand rather than taken from the generated `MessageDtoInput` / `MessageUpdateDtoInput`.

### 2. About half the operations are anonymous — ✅ Done

All 45 operations (14 queries, 31 mutations) have unique, descriptive names. `@graphql-eslint/no-anonymous-operations` and `unique-operation-name` keep it that way, and Codegen refuses duplicate names.

Left over: [`src/graphql/channels.ts`](src/graphql/channels.ts) has two mutations for the same field, `CreateChannel` and `AddChannel`. Keep one.

### 3. Repeated field selections will drift — ✅ Done

Selections are shared through 13 real fragments named `<Entity>Fields` (`UserFields`, `ChannelFields`, `MessageFields`, `MessagesResultFields`, `UrlPreviewFields`, `AttachmentFields`, and so on). The `userFields` string interpolation in `adminUsers.ts` was replaced by `...UserFields`.

Keep fragments focused and feature-owned as they grow; avoid giant "everything" fragments.

### 4. Apollo's cache is mostly bypassed — 🟡 Started (workspace channels done)

**Reference example: the workspace channel list.** It now lives in the Apollo cache and is the pattern to copy for the other domains.

- [`src/contexts/WorkspaceChannelsListContext.tsx`](src/contexts/WorkspaceChannelsListContext.tsx) reads `GetWorkspaceChannels` with `useQuery` and `cache-and-network`, holds no copy in `useState`, and exposes only `{ channels }`.
- [`src/graphql/channels.ts`](src/graphql/channels.ts) has the cache helpers `addChannelToCache`, `patchChannelInCache`, and `removeChannelFromCache`.
- The `AddChannel` mutation calls `addChannelToCache` in `update`. The other two helpers are used by the WebSocket handlers.
- WebSocket events write to the cache instead of reloading the list: `updatedChannel` patches the entity, `deletedChannel` evicts it, `newChannel` triggers one list request for the active workspace.

Two things learned doing it, which apply to every other domain:

- **`merge: true` goes in per namespace, together with that namespace's queries.** `ChannelQueries`, `MessageQueries` and the other namespace types have no `id`, so by default each query replaces its siblings in the cache, and two watched queries in one namespace would refetch each other in a loop. [`src/contexts/GraphqlProvider.tsx`](src/contexts/GraphqlProvider.tsx) sets `merge: true` for `ChannelQueries` and `AclQueries` only (the role editor loads `roleAcls` and `secureObjects` side by side). Do not switch it on for `MessageQueries` before the message list is migrated: the message queries are `cache-first` and only refetch today because the cache entry gets replaced. The `Cache data may be lost when replacing the messages field` console warning is that remaining case.
- **A WebSocket event is not always safe to write into a list.** `newChannel` is sent to every connected user regardless of `ChannelReadChannel`, and carries only `id`, `name`, `channelTypeId`, `workspaceId`, `isDm`, `memberUserIds`. The server filters `workspaceChannelList` by permission, so a new channel is fetched, not appended. Patching and evicting are safe because they are no-ops for entities the user never loaded.

Still bypassing the cache — seven `no-cache` call sites:

- [`src/contexts/UsersListContext.tsx`](src/contexts/UsersListContext.tsx)
- [`src/contexts/RolesListContext.tsx`](src/contexts/RolesListContext.tsx)
- [`src/contexts/SystemConfigProvider.tsx`](src/contexts/SystemConfigProvider.tsx)
- [`src/pages/profile/ProfilePage.tsx`](src/pages/profile/ProfilePage.tsx)
- [`src/graphql/users.ts`](src/graphql/users.ts) (two)
- [`src/graphql/channels.ts`](src/graphql/channels.ts) (direct messages)

Server state is still copied into React state in [`src/contexts/WorkspacesListContext.tsx`](src/contexts/WorkspacesListContext.tsx), [`src/contexts/DirectMessagesListContext.tsx`](src/contexts/DirectMessagesListContext.tsx), and the message list in `ChatMessageList.tsx`, and their WebSocket events trigger full reloads or patch local state. Outside channels, mutations still call `refetch()` in `onCompleted`.

Wherever that remains, there are two competing sources of truth.

Long-term target:

- Apollo cache owns server state.
- React context owns UI state such as the active workspace ID.
- Mutations return stable IDs and changed fields.
- Use `cache.modify`, generated fragments, or targeted refetches.
- Configure field policies for pagination.
- Translate WebSocket events into cache writes or selective invalidation.

Apollo's `typePolicies`, `keyFields`, pagination policies, and `possibleTypes` exist specifically for this. See [Apollo cache configuration](https://www.apollographql.com/docs/react/caching/cache-configuration).

### 5. Error handling loses useful information — ❌ Not started

The API wrappers in `src/graphql` still catch Apollo errors and throw a new generic `Error`: 33 such sites, most of them in [`src/graphql/messages.ts`](src/graphql/messages.ts) and [`src/graphql/channels.ts`](src/graphql/channels.ts). None of them pass `cause`.

That discards:

- GraphQL paths and locations.
- `extensions.code`.
- Network/server error classification.
- The original error identity and often its stack.
- Partial response data.

Other paths swallow errors entirely: [`src/contexts/WorkspaceChannelsListContext.tsx`](src/contexts/WorkspaceChannelsListContext.tsx), [`src/contexts/DirectMessagesListContext.tsx`](src/contexts/DirectMessagesListContext.tsx), and the send path in [`src/pages/client/Chat/MessageInput/MessageInput.tsx`](src/pages/client/Chat/MessageInput/MessageInput.tsx). There are no error boundaries anywhere in `src`.

The schema now documents the error codes each field can return (for example `INVALID_NICKNAME`, `NICKNAME_TAKEN`, `NOT_FOUND`), which is exactly the information the wrappers throw away.

Keep the central authentication behavior, but add:

- A normalized application error mapper that preserves `cause`.
- React error boundaries around Suspense query regions.
- User-facing mutation error messages.
- Structured reporting with operation name and safe metadata.
- Explicit `errorPolicy` only where partial data is useful.
- `RetryLink` for appropriate query network failures, not blind mutation retries.

Apollo distinguishes GraphQL, protocol, and network errors and supports explicit partial-data policies. See [Apollo error handling](https://www.apollographql.com/docs/react/v3/data/error-handling).

### 6. Chat queries are unbounded — ❌ Not started (backend first)

`listChannelMessages(channelId: Int!)` and `listThreadMessages(threadId: Int!)` still accept only an ID in the schema. There are no page-size, cursor, or page-info fields, so nothing can be done on the frontend until the backend contract changes.

For a chat application this eventually becomes a reliability problem. The backend contract should support cursor pagination:

```graphql
query GetChannelMessages(
  $channelId: Int!
  $first: Int!
  $after: String
) {
  messages {
    listChannelMessages(
      channelId: $channelId
      first: $first
      after: $after
    ) {
      edges {
        cursor
        node {
          ...MessageFields
        }
      }
      pageInfo {
        hasNextPage
        endCursor
      }
    }
  }
}
```

Then add an Apollo merge policy keyed by `channelId`. This depends on finding 4: the message list has to live in the cache before a merge policy can do anything.

### 7. Contract tests and CI are absent — 🟡 Partly done

Done:

- [`.github/workflows/ci.yml`](.github/workflows/ci.yml) runs `graphql:check`, lint, build, and tests on every pull request and on pushes to `main`.
- [`eslint.config.js`](eslint.config.js) lints the operations embedded in `.ts`/`.tsx` files with `@graphql-eslint`'s `flat/operations-recommended` set (unknown fields, anonymous operations, duplicate names, unused variables and fragments, deprecated fields).
- The `MockedProvider` stories import the production documents instead of redeclaring them.

Left:

- No backend-side check that a schema change breaks frontend operations. [GraphQL Inspector](https://the-guild.dev/graphql/inspector/docs) can diff schemas and detect breaking changes; it is not installed.
- No tests touch GraphQL. The only unit tests cover two helpers.
- `@graphql-eslint/naming-convention` is switched off.
- `storybook-static` is not in the ESLint `ignores`, so `npm run lint` reports about 22,600 errors locally once Storybook has been built. CI is unaffected and `src` is clean.

## Recommended target structure

Not adopted. Operations stay in `src/graphql/<domain>.ts`, written with `graphql()`, with types re-exported from `src/types/<domain>.ts`. That is the convention [`GRAPHQL.md`](GRAPHQL.md) documents, and it is fine at the current size.

If the app grows enough that domains need clear owners, move toward feature folders:

```text
graphql/
  schema.graphql                 # generated backend contract

src/
  graphql/
    client.ts                    # links, cache, defaults
    errors.ts
    generated/                   # Codegen output

  features/
    chat/
      api/
      components/

    workspaces/
      api/
      components/

    admin-users/
      api/
      components/
```

Two pieces of this are worth doing regardless, as part of findings 4 and 5: pull the client setup out of `GraphqlProvider.tsx` into `src/graphql/client.ts`, and add `src/graphql/errors.ts` for the error mapper.

Keep separately authored domain/view-model types only where the UI intentionally transforms API data.

## Code generation, as implemented

- Config: [`codegen.ts`](codegen.ts), client preset, `strictScalars`, `enumsAsTypes`, `useTypeImports`.
- Scalars: `UUID` and `DateTime` → `string`, `Long` → `number`, `Upload` → `File`. Do not map `DateTime` to `Date` unless a runtime layer actually converts it.
- Documents are plucked from `src/**/*.{ts,tsx}`; there are no `.graphql` operation files.
- Output is committed under `src/graphql/generated/` and never edited by hand.
- Scripts in [`package.json`](package.json): `graphql:generate`, `graphql:watch`, and `graphql:check` (regenerate, then fail if the committed output differs).

Differences from the original recipe:

- `@graphql-inspector/cli` was not added. Codegen and ESLint already validate documents, so Inspector is only needed for schema diffing.
- `fragmentMasking` is off, which lets `src/types` alias fragment types directly. Turning it on later would enforce that components only read the fields they declare, at the cost of `useFragment` calls throughout.

## Migration plan

### Phase 1 — Establish the contract (done, apart from backend automation)

- [x] Export `schema.graphql` from the backend.
- [x] Add Codegen.
- [x] Make generation and validation run in CI.
- [x] Fix scalar mappings and obvious schema/type discrepancies.
- [ ] Record the backend revision each schema export came from.
- [ ] Refresh the schema from backend CI instead of by hand.

### Phase 2 — Migrate operations (done)

- [x] Name all operations.
- [x] Replace `userFields` interpolation with fragments.
- [x] Extract repeated chat/message selections into focused fragments.
- [x] Generate typed documents and remove manual response/variable types.
- [x] Import the same generated documents in application code and stories.
- [ ] Derive the remaining message DTO types from generated input types.
- [ ] Remove the duplicate `CreateChannel` / `AddChannel` mutation.
- [ ] Move operations toward their owning features (optional, see above).

### Phase 3 — Fix data ownership (started)

- [x] Migrate one domain end to end as the reference: workspace channels.
- [ ] Remove routine `no-cache` usage (8 call sites left).
- [ ] Add `merge: true` for each remaining namespace type as its queries move to the cache (`ChannelQueries`, `AclQueries` done).
- [ ] Define list pagination policies.
- [ ] Keep active selections in React state/context, but let Apollo own fetched entities (channels done; workspaces, direct messages, messages left).
- [ ] Update or invalidate the cache after mutations and WebSocket events (channels done).
- [ ] Add pagination to messages and other unbounded lists (needs the backend).
- [ ] Add cache-policy unit tests. Jest has no `@/` alias yet, so tests cannot import `src/graphql/*.ts`.

GraphQL subscriptions are optional. The existing WebSocket layer can remain if it has a broader event protocol; it should update Apollo state more precisely rather than forcing whole-list reloads.

### Phase 4 — Team-scale governance (barely started)

- [x] Run schema validation, Codegen, TypeScript, tests, and lint in every pull request. Marking the check as required is a branch-protection setting in GitHub.
- [x] Add GraphQL ESLint rules for anonymous operations, unique names, unused variables/fragments, and deprecated fields.
- [ ] Add backend schema-diff checks and a deprecation window.
- [ ] Add operation-name telemetry and client-version headers.
- [ ] Introduce an operation registry or persisted operations. The precondition (every operation named and generated) is now met.
- [ ] Define ownership with `CODEOWNERS` by feature/API area.

## What's next

Of the original five priorities, the first four are done: the schema is exported and committed, Codegen replaced the handwritten types, every operation is named and uses fragments, and CI validates the contract. The fifth is what remains, along with the areas that were never started. In order:

1. **Message pagination.** Start with the backend contract, since it has the longest lead time.
2. **Apollo cache ownership.** Add `typePolicies`, drop `no-cache`, stop mirroring query results into `useState`, and turn WebSocket events into cache writes. Workspace channels are done and are the pattern to follow; do workspaces and direct messages next, then messages.
3. **Error handling.** Preserve `cause` in the wrappers, add error boundaries around Suspense regions, and show mutation errors to the user.
4. **Backend-side contract checks.** Record the schema's backend revision and fail backend CI on breaking schema changes.
5. **Loose ends and governance.** The unchecked Phase 2 items, the ESLint `storybook-static` ignore, GraphQL tests, then Phase 4.
