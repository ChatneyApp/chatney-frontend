# GraphQL Improvements

The biggest improvement is to introduce a versioned GraphQL schema contract and generate frontend operation types from it. Right now, Apollo is mostly being used as a transport layer; the project is not getting GraphQL's strongest benefits: compile-time contract validation, reliable normalization, safe schema evolution, and consistent team conventions.

## Executive assessment

Current strengths:

- Apollo Client 4 and strict TypeScript provide a solid base.
- Authentication and upload links are centralized in [`src/contexts/GraphqlProvider.tsx`](src/contexts/GraphqlProvider.tsx).
- Operations are grouped by domain under `src/graphql`.
- Many operations already use variables and request entity IDs.

However, the GraphQL layer is not yet ready for long-term ownership by a large team because it lacks:

1. A frontend-accessible schema contract.
2. Generated operation and variable types.
3. Schema-aware linting and CI validation.
4. Consistent operation naming and organization.
5. A deliberate Apollo cache strategy.
6. Pagination for potentially large datasets.
7. Consistent errors, testing, observability, and schema-release governance.

## Should the frontend import the backend schema?

Yes—but import the backend's generated executable schema as a build artifact, not through a relative path to somebody's backend checkout.

Recommended initial workflow:

```text
Backend source
    ↓ generate deterministic SDL
graphql/schema.graphql
    ↓ GraphQL Code Generator
typed frontend operations
    ↓ frontend CI
schema validation + TypeScript build
```

For this repository, initially commit `graphql/schema.graphql`, with these rules:

- It is generated by the backend and never hand-edited.
- It represents a known backend revision or release.
- A backend command or CI job refreshes it deterministically.
- Frontend CI validates every operation against it.
- Backend CI checks whether a schema change breaks registered frontend operations.

Later, when the projects and teams grow, publish the schema through one of:

- A versioned `@chatney/api-schema` package.
- A schema registry such as GraphOS or GraphQL Hive.
- A cross-repository CI artifact pinned to a backend commit.

Avoid using a live development endpoint as the only Codegen schema source. That makes builds dependent on whichever backend happens to be running and prevents reproducible CI.

A schema artifact enables autocomplete, operation validation, generated variables/results, union handling, mock generation, and contract diffs. Apollo also recommends generating TypeScript definitions from the schema and operations rather than manually typing hooks. See [Apollo's TypeScript guidance](https://www.apollographql.com/docs/react/v3/development-testing/static-typing) and [GraphQL Code Generator](https://the-guild.dev/graphql/codegen).

## What is currently missing or wrong

### 1. Manual types can lie about the API

Most response types are handwritten, for example in:

- [`src/graphql/messages.ts`](src/graphql/messages.ts)
- [`src/graphql/auth.ts`](src/graphql/auth.ts)
- [`src/graphql/adminUsers.ts`](src/graphql/adminUsers.ts)

TypeScript only verifies that the application code agrees with those declarations. It does not verify that the declarations agree with the backend.

There are already warning signs:

- GraphQL timestamps are typed as JavaScript `Date` objects, but JSON responses arrive as strings unless explicit runtime deserialization is added. See [`src/types/attachments.ts`](src/types/attachments.ts) and [`src/types/messages.ts`](src/types/messages.ts).
- `ChannelGroup.workspaceId` is a `string`, while workspace-related GraphQL operations use `Int!`. See [`src/types/channelGroups.ts`](src/types/channelGroups.ts).
- `GET_CHANNEL` expects a response property named `GetChannel` and fields such as `Id` and `Name`, unlike the lowercase conventions used elsewhere. See [`src/graphql/channels.ts`](src/graphql/channels.ts).
- Mutation variables are frequently untyped because their documents are plain `DocumentNode` values.

Code generation would surface these inconsistencies immediately.

### 2. About half the operations are anonymous

There are approximately 43 operations in `src/graphql`; 22 are anonymous.

Examples include:

- [`src/graphql/channelGroups.ts`](src/graphql/channelGroups.ts)
- [`src/graphql/roles.ts`](src/graphql/roles.ts)
- [`src/graphql/systemConfig.ts`](src/graphql/systemConfig.ts)

Every operation should have a globally unique, descriptive name:

```graphql
mutation CreateChannelGroup($input: ChannelGroupDtoInput!) { ... }
query GetWorkspaceChannelGroups($workspaceId: Int!) { ... }
mutation UpdateSystemConfigValue($input: ConfigInput!) { ... }
```

Names are essential for logs, tracing, operation registries, persisted operations, and production debugging.

### 3. Repeated field selections will drift

Message, attachment, URL preview, and user selections are repeated extensively in [`src/graphql/messages.ts`](src/graphql/messages.ts).

`adminUsers.ts` tries to solve this with raw string interpolation:

```ts
const userFields = `...`;
```

That pattern in [`src/graphql/adminUsers.ts`](src/graphql/adminUsers.ts) is difficult for static GraphQL tooling to validate and compose. Replace it with a real fragment:

```graphql
fragment AdminUserFields on User {
  id
  nickname
  fullName
  email
  avatarUrl
  active
  verified
  banned
  muted
  roleId
}
```

Use focused, feature-owned fragments—not giant "everything" fragments.

### 4. Apollo's cache is mostly bypassed

The client has an unconfigured `InMemoryCache` in [`src/contexts/GraphqlProvider.tsx`](src/contexts/GraphqlProvider.tsx), while numerous providers use `no-cache`, including:

- [`src/contexts/UsersListContext.tsx`](src/contexts/UsersListContext.tsx)
- [`src/contexts/RolesListContext.tsx`](src/contexts/RolesListContext.tsx)
- [`src/contexts/WorkspaceChannelGroupsListContext.tsx`](src/contexts/WorkspaceChannelGroupsListContext.tsx)
- [`src/pages/profile/ProfilePage.tsx`](src/pages/profile/ProfilePage.tsx)

Server state is then copied into React context state, while WebSocket events trigger full refetches. For example, [`src/contexts/WorkspacesListContext.tsx`](src/contexts/WorkspacesListContext.tsx) duplicates the Apollo result into local state.

This creates two competing sources of truth.

Long-term target:

- Apollo cache owns server state.
- React context owns UI state such as the active workspace ID.
- Mutations return stable IDs and changed fields.
- Use `cache.modify`, generated fragments, or targeted refetches.
- Configure field policies for pagination.
- Translate WebSocket events into cache writes or selective invalidation.

Apollo's `typePolicies`, `keyFields`, pagination policies, and `possibleTypes` exist specifically for this. See [Apollo cache configuration](https://www.apollographql.com/docs/react/caching/cache-configuration).

### 5. Error handling loses useful information

Several API wrappers catch Apollo errors and create a new generic `Error`, for example [`src/graphql/auth.ts`](src/graphql/auth.ts) and [`src/graphql/messages.ts`](src/graphql/messages.ts).

That discards:

- GraphQL paths and locations.
- `extensions.code`.
- Network/server error classification.
- The original error identity and often its stack.
- Partial response data.

Other paths swallow errors entirely, such as [`src/contexts/WorkspaceChannelsListContext.tsx`](src/contexts/WorkspaceChannelsListContext.tsx).

Keep the central authentication behavior, but add:

- A normalized application error mapper that preserves `cause`.
- React error boundaries around Suspense query regions.
- User-facing mutation error messages.
- Structured reporting with operation name and safe metadata.
- Explicit `errorPolicy` only where partial data is useful.
- `RetryLink` for appropriate query network failures, not blind mutation retries.

Apollo distinguishes GraphQL, protocol, and network errors and supports explicit partial-data policies. See [Apollo error handling](https://www.apollographql.com/docs/react/v3/data/error-handling).

### 6. Chat queries are unbounded

`listChannelMessages` and `listThreadMessages` accept only an ID in [`src/graphql/messages.ts`](src/graphql/messages.ts). There are no page-size, cursor, or page-info selections.

For a chat application this eventually becomes a reliability problem. The backend contract should support cursor pagination:

```graphql
query GetChannelMessages(
  $channelId: Int!
  $first: Int!
  $after: String
) {
  messages {
    listChannelMessages(
      channelId: $channelId
      first: $first
      after: $after
    ) {
      edges {
        cursor
        node {
          ...ChatMessageFields
        }
      }
      pageInfo {
        hasNextPage
        endCursor
      }
    }
  }
}
```

Then add an Apollo merge policy keyed by `channelId`.

### 7. Contract tests and CI are absent

There is no project CI configuration, Codegen setup, or GraphQL-aware ESLint configuration. The current [`eslint.config.js`](eslint.config.js) handles only TypeScript and React.

Storybook has some `MockedProvider` coverage, but several stories redeclare operation text rather than importing the production operation. That permits production and mock documents to drift.

GraphQL Inspector can validate documents against a schema and detect breaking schema changes. See [GraphQL Inspector](https://the-guild.dev/graphql/inspector/docs) and its [document validation guide](https://the-guild.dev/graphql/inspector/docs/essentials/validate).

## Recommended target structure

```text
graphql/
  schema.graphql                 # generated backend contract

src/
  graphql/
    client.ts                    # links, cache, defaults
    errors.ts
    generated/                   # Codegen output

  features/
    chat/
      api/
        ChatMessageFields.graphql
        GetChannelMessages.graphql
        CreateMessage.graphql
      components/

    workspaces/
      api/
      components/

    admin-users/
      api/
      components/
```

Keep separately authored domain/view-model types only where the UI intentionally transforms API data. Do not manually recreate GraphQL result or input types in `src/types`.

## Code generation recipe

Install:

```bash
npm install -D @graphql-codegen/cli @graphql-codegen/client-preset @graphql-eslint/eslint-plugin @graphql-inspector/cli
```

Suggested `codegen.ts`:

```ts
import type { CodegenConfig } from '@graphql-codegen/cli';

const config: CodegenConfig = {
  schema: './graphql/schema.graphql',
  documents: ['src/**/*.{graphql,ts,tsx}'],
  ignoreNoDocuments: false,
  generates: {
    './src/graphql/generated/': {
      preset: 'client',
      config: {
        useTypeImports: true,
        strictScalars: true,
        defaultScalarType: 'unknown',
        scalars: {
          UUID: 'string',
          DateTime: 'string',
          Upload: 'File',
        },
      },
    },
  },
};

export default config;
```

Adjust scalar names after inspecting the real schema. Do not map `DateTime` to `Date` unless a runtime layer actually converts it.

Add scripts:

```json
{
  "graphql:generate": "graphql-codegen",
  "graphql:watch": "graphql-codegen --watch",
  "graphql:validate": "graphql-inspector validate \"src/**/*.graphql\" graphql/schema.graphql"
}
```

Codegen's client preset produces typed documents and validates variables and results against the schema. See the [client preset documentation](https://the-guild.dev/graphql/codegen/plugins/presets/preset-client).

## Migration plan

### Phase 1 — Establish the contract

- Export `schema.graphql` from the backend.
- Add Codegen and GraphQL Config.
- Make generation and validation run in CI.
- Record all existing validation failures instead of weakening generated types.
- Fix scalar mappings and obvious schema/type discrepancies.

### Phase 2 — Migrate operations

- Name all operations.
- Replace `userFields` interpolation with fragments.
- Extract repeated chat/message selections into focused fragments.
- Generate typed documents and remove manual response/variable types.
- Import the same generated documents in application code, tests, and stories.
- Move operations toward their owning features.

Start with a small vertical slice such as profile or admin users, then migrate chat.

### Phase 3 — Fix data ownership

- Remove routine `no-cache` usage.
- Define entity identity and list pagination policies.
- Keep active selections in React state/context, but let Apollo own fetched entities.
- Update or invalidate the cache after mutations and WebSocket events.
- Add pagination to messages and other unbounded lists.
- Add cache-policy unit tests.

GraphQL subscriptions are optional. The existing WebSocket layer can remain if it has a broader event protocol; it should update Apollo state more precisely rather than forcing whole-list reloads.

### Phase 4 — Team-scale governance

- Require schema validation, Codegen, TypeScript, tests, and lint in every pull request.
- Add GraphQL ESLint rules for anonymous operations, unique names, unused variables/fragments, and deprecated fields.
- Add backend schema-diff checks and a deprecation window.
- Add operation-name telemetry and client-version headers.
- Introduce an operation registry or persisted operations only after every operation is named and generated.
- Define ownership with `CODEOWNERS` by feature/API area.

## Priority order

If only five things are implemented, do them in this order:

1. Export and pin the backend schema.
2. Add GraphQL Code Generator and remove handwritten operation types.
3. Name every operation and replace raw/repeated selections with fragments.
4. Establish CI contract validation.
5. Redesign Apollo cache ownership and add message pagination.

This sequence gives immediate correctness and developer-experience gains without requiring a risky rewrite of the application.
